# 更新守卫

> `AGENTS.md` 规则 3 的正文。**改自动更新拦截、更新页开关、`-KeepUpdates` / `-DisableUpdates` 之前必须读完本文件。**

「设置 > 更新」页里有**两个**汉化工具注入的开关，改任何一个之前先分清是哪个：

| | Postman 自动更新 | 汉化版本更新检查 |
|---|---|---|
| 管什么 | Postman 官方升级（升级会覆盖汉化） | 本汉化包 GitHub 有没有新版 |
| 默认 | **关闭**（拦截才安全） | **开启** |
| 偏好文件 | `postman-zh-updates.json` | `postman-zh-version-check.json` |
| 文件不存在时 | 视为关闭 | 视为开启 |
| 实现位置 | `安装汉化.ps1` 注入 `main.js` 的单行守卫 | `payload/zh-version-check-main.js` |
| 命令行 | `updates on\|off` | `zh-updates on\|off\|check` |
| 会不会改文件 | 会（允许后 Postman 自己升级） | **不会**，只提示，永不下载不安装 |

两份状态互相独立（有测试覆盖：切一个不影响另一个）。下面先讲第一个，最后一节讲第二个。

## Postman 自动更新守卫

**更新守卫是开关，不是墙**：入口的 `-KeepUpdates` 表示「保留官方自动更新、不装守卫」，它在 `统一入口.ps1` 里取反后传给 `安装汉化.ps1` 的 `-DisableUpdates`（默认即拦截）。装守卫时**不要**改 `isUpdateEnabled`（会让"设置>更新"页报"出现了一些问题"连接错误）。当前实现在 `main.js` 顶部装一个运行时守卫，并用版本无关锚点把 `downloadUpdate`、`restartAppToUpdate` 改写成**条件**分支；更新页仍应正常显示"已是最新版本"。找不到可确认的源码锚点时应报错，而不是假装成功。

守卫每次更新调用都读 `%APPDATA%\Postman\postman-zh-updates.json`（缓存约 1 秒），**文件不存在即视为关闭**，所以默认行为和以前一样是拦截。允许时走 Postman 原始实现（覆盖前已 `bind` 保存）。三个入口写同一个文件：Postman「设置 > 更新」页里注入的开关（经守卫注册的 `postman-zh:updates:get/set` IPC）、`postman-zh.bat updates on|off`、TUI 菜单第 10 项。

改这块时注意：**写偏好文件必须无 BOM**，守卫用 `JSON.parse` 读，BOM 会让解析失败并静默退回"已关闭"；`验证汉化.js` 校验的是"守卫已安装"（`updatePatch.installed`），不是"当前已拦截"——当前是否拦截由用户的开关决定，不该让 `verify` 失败。

**开关是滑动开关，单击即切换**：页面开关做成 `role=switch` 的滑动样式（轨道 + 圆钮 + 右侧「已开启/已关闭」文字），单击直接写偏好、无需二次确认。曾经为防误触加过"点两次确认开启"，但用户觉得不方便，已改回单击（2026-08-25）。防自动化误点改为只靠按钮上的 `data-postman-zh-audit-skip="true"` 标记（审计脚本必须跳过带这个属性的元素，这条同时记在 `AGENTS.md` 规则 3）。渲染状态只改 `data-enabled`/`aria-checked` 和 label 文字，`refreshUpdateToggle`（900ms 轮询）和初始 `updates:get` 会照常把外部（命令行）改动同步回按钮。

**注入锚点不能只认一个**：更新页在不同状态下渲染的是完全不同的组件。`findUpdateToggleSlot()` 按三级兜底找位置——优先 `.settings-update-changelog-container`（“有可用更新”的发布说明视图），其次 `.settings-autoupdate`（旧版“已是最新”里 Postman 自带的自动下载开关），都没有时再靠 `[class*="update-"][class*="__button"]`（`update-not-available__button`、`update-idle__button` 这类语义类名）确认当前在更新页，插到 `.settings-tab-contents` 里状态块之后。12.25.5 / 12.25.7 / 12.26.3 的“已是最新”状态前两个锚点**都不存在**，只有第三级能兜住；换 Postman 版本后要重新确认这三级还有效。

**两个开关共用整宽设置区，放在发布说明上方**（2026-09-07）：发布说明的父容器可能是横向 flex / grid，直接把开关插成它的兄弟节点会让开关和说明并排互相挤压。`stackedUpdateSlot()` 越过横向包装层，在纵向容器里落位；两个开关统一放进 `#postman-zh-update-controls`，使用独立的 `postman-zh-update-panel*` 样式，标题和开关左右对齐，描述独占下一行。保留 Postman 自己的容器样式。每轮重新定位同一个设置区，处理“已是最新 → 有可用更新”的状态切换，保持按钮节点及事件处理器；离开更新页时连同外层设置区一起清理。

## 汉化版本更新检查（2026-09-01 加入）

只做一件事：定期问 GitHub「本汉化包有没有新版」，有就在右下角浮个提示条。**永不下载、永不安装、永不改任何文件**，用户点「打开发布页」才跳浏览器。

**为什么放主进程**（`payload/zh-version-check-main.js`，由 `Patch-VersionCheck` 拷进 asar 的 `js/` 并在 `main.js` 顶部 `require`）：渲染进程受 Postman 自己的 CSP 约束，`connect-src` 不保证放行 `api.github.com`；主进程没这层限制。而且这段有网络请求、超时、节流和 JSON 解析，压成 `main.js` 里的单行 IIFE 没法维护——所以走 `Patch-Preload` 已验证过的「独立文件 + 注入处 require」路子，注入的那一行只负责 `require().install(ipcMain)`。

**本机版本号从哪来**：`app.asar` 的 `package.json` version，也就是 Postman 版本号。汉化包的 Release 标签与它一一对应（`v12.27.0` ↔ `app-12.27.0`），所以直接比这个，不另存版本文件（会和实际安装脱节）。`localVersion()` 有两条取法：asar 内读上一级 `package.json`；命令行上下文（`zh-updates check` 直接 require 本文件）读不到，退而扫 Postman 安装目录名 `app-<版本>` 取最高版本。都取不到就返回空串，检查结果为 `error`。**本机 Postman 的版本号只说明兼容版本，不证明该版本汉化产物已在 GitHub 发布。**

### 发布状态必须核实附件（2026-09-07 修）

旧实现仅判断 `isNewer(remote, local)`，把所有 `false` 都显示成“已是最新版”：远端仍是 v12.26.3、本机已到 12.26.5，甚至响应缺标签时都会误报。现改为严格的数字段比较，并要求 GitHub 返回公开稳定 Release、有效发布时间，以及 `state=uploaded` 且大小大于零的 **`app.asar` 和同版本 `Postman-cn-<版本>-win64.zip` 两个附件**。查询只检查元数据，不下载文件。

| 条件 | 状态 | 页面与命令行说明 |
|---|---|---|
| 远端与本机相等，且两个附件齐全 | `latest` | 已是 GitHub 最新已发布汉化版本，显示远端标签 |
| 远端更高，且两个附件齐全 | `update-available` | 有已发布的新汉化版本 |
| 本机更高，远端仍是旧版 | `local-unpublished` | 本机对应版本尚未发布，并列出 GitHub 最新已发布版本 |
| 标签存在但附件缺失、空文件、上传中或 ZIP 版本不匹配 | `release-incomplete` | 汉化产物尚未上传完整 |
| 无效标签、草稿、预发布、无效响应或本机版本未知 | `error` | 查询未确认，保持静默，不显示最新版 |

前三种正常结果按一小时缓存，进入更新页、「立即检查」按钮和 `zh-updates check` 可刷新普通缓存；缺附件的结果同样可强制重查。`scripts/runtime/验证版本检查.js` 用真实可能出现的版本与附件组合覆盖这些分支，以及缓存、并发、关闭竞态和网络故障，由 `verify` / `install` 自动运行；网络和偏好文件均隔离在内存中。

**五条必须守住的边界**：

- **默认开启，但关掉就一个请求都不发**。`check()` 开头先读偏好，关闭时直接返回 `status:"disabled"`，不进 `fetchLatest()`。
- **自动检查缓存一小时**，`force=true`（进入更新页、点击「立即检查」、刚打开检查开关、`zh-updates check`）可刷新。GitHub 匿名接口是每 IP 每小时 60 次。
- **撞限额要按 `x-ratelimit-reset` 退避，且连 `force` 也挡**。403/429 时按响应头算出恢复时刻存进 `cached.rateLimitedUntil`，那之前一律走缓存——否则用户狂点「立即检查」只会让限额更久，每次还要等一个必然失败的往返。
- **任何失败都静默**：超时、断网、非法 JSON、`tag_name` 缺失，全部落到 `status:"error"`，不弹任何东西，也不冒充最新版。设置页会区分「限额用尽（过一会儿自动恢复）」和「查不到（检查网络）」两种说法。
- **`openExternal` 的 URL 写死在主进程**，IPC 不接受渲染进程传入的地址，避免变成任意外链跳转的通道。

**提示条**（`showVersionBanner`）：右下角 fixed 浮层，不挡工作区、不弹模态，三个按钮——「打开发布页」「以后再说」「不再提示此版本」。最后一个把版本号写进偏好的 `dismissedTag`，之后同一版本不再弹，但设置页仍显示有新版。后续检查发现更高版本时更新已有提示条。

**立即 + 手动 + 每小时检查**（2026-09-08）：启动时 IPC 就绪即检查，打开「设置 > 更新」页时刷新一次，新增「立即检查」按钮。四个入口共用 `requestVersionCheck()` 的在途 Promise；检查中按钮禁用并显示「检查中…」，结束或失败后恢复。每次完成后重新安排唯一的小时计时器，手动检查也重置它；重复 `run()` 不叠加计时器。采用完成后计时，避免固定 interval 比主进程缓存到期略早、结果漏掉一轮。IPC 暂未就绪时允许后续巡检重新启动。

关闭时手动按钮禁用，主进程不发新请求；已发出的请求返回时重新读取偏好，关闭后不弹提示，也不让迟到的结果改回开关。关闭再开启会刷新普通缓存，但仍保留 GitHub 的限额退避。`scripts/runtime/验证版本检查界面.js` 使用真实渲染器函数和内存 DOM / IPC / 虚拟时钟，覆盖立即检查、页面重入、手动刷新、连续小时调度、忙碌状态、并发和迟到响应，由 `verify` / `install` 一起运行。

**开关同步**：和 `refreshUpdateToggle` 同一个道理，`refreshVersionCheckToggle` 在 900ms 轮询里只同步开关状态、**不重查版本**，所以命令行 `zh-updates on|off` 后已打开的设置页会自动回正，且这轮轮询不产生网络请求。

### 不要再加应用内下载（2026-09-02 做过又拆掉）

曾经给这栏加过「下载新版」：后台拉 `app.asar`、校验体积 + SHA-256 + asar 头里的版本、支持 Range 续传、进度轮询，19 项测试全过，包括真实下载 155 MB 用 35 秒。**但整个功能在真实场景下永远走不到 ready**，因为两个条件互斥：

- 触发下载需要 `tag > 本机版本`
- 允许安装需要 `包内 Postman 版本 == 本机版本`（跨版本混装必坏：`app.asar` 和目录里的 Electron 二进制、`.pak` 资源是配套的）

而本项目的版本约定是 `tag == 包内 Postman 版本`（`v12.26.3` ↔ `app-12.26.3`），所以只要提示了有新版，下载回来的包就一定被版本闸门拒收。

**当时的测试为什么没抓到**：假 API 那例我构造了 `tag=v12.26.0` 而包内版本 `12.25.7` 的组合——现实中不存在；真实下载那例把本机版本伪装成 12.24.0 去下 v12.25.7 的资产，最后确实被闸门拦住，我却把这个拒收当成「闸门正确工作」的证据，没想到真实情形每次都会撞同一堵墙。**教训：测试用的输入组合必须是真实世界可能出现的，否则通过率再高也说明不了功能可用。**

根子上是「升级汉化在本项目里等于升级 Postman」——得换 `app-<新版>` 目录再打补丁（见 [升级与发布.md](./升级与发布.md) 第 1 节），不是替换单个 `app.asar` 能解决的。真要做应用内升级，得下**完整绿色版 zip 或 nupkg** 并走完整安装流程，那是另一个量级的工程。所以现在只把用户送到发布页。

### 面板只能出现在「更新」页（2026-09-02 修）

Postman 的设置对话框**切页签时不卸载已渲染过的页面**：更新页那个 `update-not-available__button` 会隐藏但留在 DOM 里。所以第三级锚点若只判断「元素存不存在」，在「通用」「主题」等任何页签上都会命中，面板被插进共享容器 `.settings-tab-contents` —— 用户看到的就是「每个设置页都有更新开关」。

两处都得改，缺一不可：

- `findUpdateToggleSlot()` 的三级锚点都要过 `isVisibleNode()`（`offsetParent === null` 排除 `display:none` 和祖先隐藏，再要求 `getBoundingClientRect()` 有实际尺寸）。第二级从 `querySelector` 改成遍历 `querySelectorAll` 逐个查可见性——隐藏的旧页签节点不算。
- 光靠「插入时判断」不够：面板一旦在更新页插好，切走时会跟着共享容器留下。`removeStrayUpdatePanels()` 每轮轮询确认当前是否还在更新页，不在就摘掉。**调用顺序必须先摘再插**，反了会立刻插回去。

`isOwnPanel()` 要同时排除 `postman-zh-update-controls`、`postman-zh-update-switch` 和 `postman-zh-version-check` 三个 id，也兼容旧版复用 `settings-autoupdate` 类名的面板，避免拿自己的节点当锚点。它里面的 id 写字面量而不是引用 `VERSION_CHECK_BOX_ID`：那个常量声明在函数下方，靠 `var` 提升虽不报错但取值时机就依赖 IIFE 执行顺序了。

**验证这块时注意等待时间**：进更新页后 Postman 要先花约 4 秒查更新，期间显示「正在检查更新...」，三个锚点一个都没渲染，`findUpdateToggleSlot` 正确返回 null。只等 2.5 秒会误判成注入失败——`_generated/diag-settings-tabs2.js` 因此给更新页 15 秒轮询窗口。那个脚本还有一个坑值得记：枚举页签必须限定在 `[data-testid="settings-modal"]` 内、且只取「位于 `.settings-tab-contents` 左边」的短文本叶子节点，否则会把主界面的集合筛选器（「全部 0」「正在关注 0」）当成设置页签，点在模态背后、对话框根本没切页，读到的还是上一页状态——那会产生假 `true`。

`验证汉化.js` 校验的是「补丁已安装」（`versionCheckPatch.installed`，查 `main.js` 里的 require 钩子 + 实现文件里的四个 IPC 通道名），不是「当前开没开」。注意 `VERSION_CHECK_IPC_MARKERS` 在 `js/zh-version-check-main.js` 里而**不在** `main.js` 里，所以安装期临时 `main.js` 的交叉比对只能用 `MAIN_JS_PATCH_MARKERS` 这个子集——否则 `onlyInAppAsar` 会永远列出那几条，看着像安装不一致。
