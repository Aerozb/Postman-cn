# 升级与发布

升级 Postman、提交或发布前阅读本文。普通补词条见 [维护指南](./维护指南.md)，命令参数见 [脚本说明](../scripts/README.md)。

## 1. 升级 Postman

1. 查询官方状态：`https://dl.pstmn.io/update/status?currentVersion=<当前版本>&arch=64&platform=win`。该接口可能只给下一步版本：若返回更高版本，继续以返回版本查询，直到 HTTP 204/空正文确认无后继；不要把首个返回版本直接称为最新版。记录完整递增链，异常响应、版本不递增或达到查询上限时停止并查明原因。
2. full nupkg 从 Squirrel feed 获取：`https://dl.pstmn.io/update/win64/<当前版本>/stable`。响应给出 SHA1、下载 URL 与字节数，使用返回的真实地址；若只给中间版，以上一步递增链中最终版的前一版查询 feed，核对目标为已确认的最终版本。
3. 下载到官方 `packages/`，核对 SHA1、大小和文件头。nupkg 是 ZIP（`PK`）；普通版本下载 URL 可能给出 EXE（`MZ`），两者不混用。
4. 将 nupkg 的 `lib/net45` 解压为 `app-<新版本>`，在 `packages/RELEASES` 增加 `<SHA1> <文件名> <字节数>`。只按确认的官方版本和包内容操作。
5. 执行 `postman-zh.bat install -CleanOldVersions`。默认验证通过后再清理旧版，保留当前版本及英文备份。
6. 按 [官方 i18n 清单](./官方i18n清单与生成规则.md) 重新确认资源地址并抓取新增文案，结合用户截图反馈补齐；涉及本地兜底页或官方资源未收录的文案时再按需补查源码。

文档示例使用 `<版本>`，不要把某次“当前版本”写成长期固定值。历史兼容性样本保留日期和范围，不能当成新版运行验证。

## 2. 发布前检查

```powershell
.\postman-zh.bat test
.\postman-zh.bat help
.\postman-zh.bat install
.\postman-zh.bat verify
.\postman-zh.bat publish -CheckOnly
 git diff --check
 git status --short
```

`test` 运行离线语法、文档、翻译与工具链回归，包含发布预检的内存桩测试；`publish -TestOnly` 可单独运行发布预检回归。`publish -CheckOnly` 会真实访问 GitHub 核验当前账号和仓库权限，但不提交、推送或上传。

首次升级加载远端页面时，CDP 目标出现不代表菜单已经初始化。`verify` 会在限定时间内只读轮询 DOM、汉化运行时及右键菜单管理器的汉化标记，再执行探针；超时仍判失败，不跳过菜单验证。

`verify` 检查已安装的 payload、共享固定翻译样例、DOM 数据保护、组合文案、菜单及补丁标记。修改词典、RULES 或 PHRASES 后，还要跑更广语料对比：

- 批量补词条或升级时使用本轮官方 i18n；单点修复使用反馈原文及受影响的关联文案。源码补查仅用于这些来源未覆盖的情况，不要求每轮全界面扫描。
- 用 `git show HEAD:payload/zh-localize.js` 作提交基线，与工作区源码分别通过 `scripts/lib/汉化沙箱.js` 加载；逐条比较真实 `translate()`。
- 人工复核“丢失已有中文”和“新增半截”的输入，目标是无质量回退。临时全量语料及诊断脚本放 `_generated`，固定 `test` 不依赖这些临时文件。
- 仅重构时可用改前、改后的最终词典及固定样例证明译文未变；涉及页面行为时重走相应界面，并按需做定点 DOM / 跨帧测试。诊断的部分结果不作完整通过结论。

`AGENTS.md` 保持在 32 KiB 内，测试和发布预检均检查该限制。不要提交 asar、备份、解包目录、临时截图、`_generated` 或用户数据；已有供 README 展示的脱敏截图是项目资源，不属于临时产物。

## 3. 提交与 Release

- 当前仓库通常直接维护 `main`；需要评审再建分支。提交首行用中文概括，正文写原因；AI 协作提交按项目约定加 `Co-Authored-By` 尾注。
- **执行 publish 前检查全部工作区改动**：发布脚本会 `git add -A`、自动提交并推送。保持待发布内容可审阅，别混入无关文件。`-SkipRelease` 仍可能提交、推送，并非只读预检。
- 默认普通 push；`-Force` 会强制覆盖远端历史，仅在明确需要时使用。`-Yes` 只跳过交互确认。
- 标签为 `v<版本>`，附件为 `app.asar` 和 `Postman-cn-<版本>-win64.zip`，都必须对应同一 Postman 版本和本轮构建。
- 发布预检只读解析 asar 的 `package.json`，以包内 Postman 版本为准，核对版本目录及显式标签。另核对官方 nupkg 的版本、大小、SHA1 和程序版本，避免混用运行文件。
- 先创建草稿、上传两个附件，核对名称、大小和 GitHub SHA-256，再公开并标为 latest。失败返回非零并保留本地产物。
- `-ReplaceRelease` 会删除旧 Release、附件及远端同名 Git 标签，再按当前 HEAD 重建；同版本重打补丁时重新构建 ZIP，避免复用旧附件。旧资产下载计数也会重置。
- 发布后核对 `gh release view v<版本> --json assets` 及 GitHub latest API，确认公开状态、标签和两个附件，而不只看终端成功文字。

## 4. 网络与权限

预检固定核验 GitHub.com 当前活动账号及目标仓库实际写权限。网络/服务端 5xx 的只读查询最多尝试 3 次；凭据失效、限额和权限错误分别报告，写操作不自动重试。Release 查询失败不视为“版本不存在”。

没有显式代理变量时，发布进程可继承 Windows 已启用的静态 HTTP(S) 代理；已有代理环境变量和 `NO_PROXY` 优先，不修改系统代理、Git 全局设置或 gh 登录。细粒度凭据需覆盖目标仓库的 Contents 写权限，最终由 GitHub 校验实际写入。

## 5. 发布后的上一版更新提示验收

1. 等新版 Release 公开且两个附件完整后，从紧邻的上一条稳定 Release 下载**完整绿色 ZIP**，校验 GitHub 的大小和 SHA-256，再解压到同级 `_generated` 内。保留上一版自带的 asar、Electron 和原生模块，不用新版文件覆盖旧包。
2. 通过 `postman-zh.bat stop` 关闭当前实例。仅在测试命令进程中把 `APPDATA`、`LOCALAPPDATA` 指向 `_generated` 下的新建空目录，再用 `start -PostmanDir <旧版 app 目录> -UserDataDir <临时 APPDATA>/Postman` 启动。只改变 `APPDATA` 并不保证 Electron 数据隔离；`--user-data-path` 和汉化偏好目录须同时隔离。
3. 重新读取临时目录的 `DevToolsActivePort`，先被动观察真实启动提示，再读取已安装版本检查模块的状态。确认本机旧版本、真实 GitHub latest、新版完整附件、`update-available` 状态与可见中文提示条一致；不注入新版 payload，不替换接口返回，也不伪造本机版本。
4. 按需只截取提示条，报告和截图复用公共诊断工具。不要点击忽略版本、更新开关或涉及用户数据的按钮；无需登录原有账号。
5. 测试结束通过统一入口停止旧版，恢复测试命令的进程环境，启动正式新版并再次 `verify`。核对日常两个更新偏好的文件哈希未变。报告区分“接口发现更新”与“界面实际出现提示”，两项分别记录。

同标签重发不是较高的 Postman 版本；当前检查按版本号比较，不以附件内容变化判更新。上述验收使用真实的较高稳定版本。
